# PRD：octo-cli 命令输出支持脚本友好消费

- 状态：Draft v0.1
- 关联 Issue：https://github.com/CiccyZ/octo-cli-agent-demand-pool-zx/issues/10
- 类型：Feature / UX
- 优先级：P2
- 模块：octo-cli 输出格式 / 自动化脚本集成体验
- 来源：Octo 群用户反馈（AINOL考官转述王宜林反馈）

## 1. 背景

用户反馈：命令输出没法直接给脚本使用，每次都需要自己解析一堆内容，并追问“这个是不是没做”。

这说明用户在自动化场景中需要稳定、可预期、容易提取字段的命令输出，而不是主要面向人阅读的文本。即使产品已有部分结构化输出能力，如果用户无法发现、无法稳定使用，或不同命令输出口径不一致，仍会造成“不能直接给脚本用”的体验问题。

## 2. 用户问题

用户在 shell、CI 或其他自动化脚本中调用 `octo-cli` 后，希望直接读取命令结果中的字段并进入下一步处理。当前用户感知是输出不够脚本友好，需要自行解析文本或非稳定结构，导致脚本脆弱、维护成本高，也容易因为输出文案变化而失效。

## 3. 目标用户

- 用 `octo-cli` 写自动化脚本的开发者和运维用户。
- 在 CI/CD、批处理、内部工具中集成 `octo-cli` 的团队。
- 需要稳定读取命令结果、错误码、分页结果或对象 ID 的高级用户。

## 4. 用户故事

作为一个用 `octo-cli` 写脚本的用户，
我希望命令能提供稳定、文档化、机器可读的输出，
以便我能直接把输出传给脚本后续步骤，而不是解析人类可读文本。

作为一个维护自动化流程的用户，
我希望成功输出、失败输出和退出码规则一致，
以便脚本可以可靠判断成功、失败和错误类型。

## 5. 需求范围

范围内：

- 用户可以清楚知道哪些输出格式适合脚本使用。
- 支持稳定结构化输出口径，让脚本能读取固定字段，而不是解析展示文案。
- 成功输出与失败输出需要有清楚、稳定、文档化的结构说明。
- 退出码规则需要清楚说明，方便脚本判断命令是否成功。
- 常见脚本场景需要提供可复制示例，例如提取 ID、处理列表分页、读取错误码、过滤字段。
- 对已有命令的脚本友好输出口径进行一致性梳理；如果个别命令存在例外，需要在文档中标明。

## 6. 非目标

本需求不包含：

- 不重新设计所有人类可读输出样式。
- 不强制移除表格、文本等面向人阅读的输出格式。
- 不承诺所有历史脚本无需调整。
- 不新增复杂脚本运行器或工作流编排能力。
- 不承诺具体技术实现方式。

## 7. 体验要求

- 用户应能一眼区分“给人看的输出”和“给脚本用的输出”。
- 脚本友好输出应尽量稳定，避免文案变化导致脚本解析失败。
- 错误信息应既能让人看懂，也能让脚本判断错误类型和下一步处理。
- 文档示例应覆盖用户最常见的自动化动作，而不是只说明参数名。
- 如果某些命令暂不支持脚本友好输出，应明确提示用户当前限制和替代方案。

## 8. 验收标准

1. 用户可以在帮助信息或文档中找到适合脚本使用的输出格式说明。
2. 用户可以通过结构化输出模式获取命令成功结果中的稳定字段。
3. 用户可以通过结构化错误输出和退出码判断命令失败原因。
4. 文档提供至少三个可复制脚本示例：提取对象 ID、处理列表或分页、根据错误码分支处理。
5. 常用命令的脚本友好输出规则保持一致；存在例外时，文档明确列出例外和原因。
6. 人类可读输出仍可继续使用，不影响已有普通交互场景。
7. 输出字段或格式若存在稳定性等级，应在文档中说明哪些字段适合脚本依赖。

## 9. 风险与待确认问题

- 需要确认用户反馈中具体遇到的是哪个命令或哪一类命令。
- 需要确认现有结构化输出能力是否覆盖全部常用命令，还是只有部分域命令支持。
- 需要确认默认输出是否应保持人类可读，脚本场景通过显式参数启用结构化输出。
- 需要确认哪些字段承诺稳定，哪些字段只用于展示或调试。
- 需要确认错误输出、分页输出、空结果输出在各命令中的一致性。
